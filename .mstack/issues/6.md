## Problem and goal

Check that a package conforms to the format without compiling it or running its contents.

## In scope

1. Ship a small offline validator with the spec repo’s versioned schemas. Check structured fields, missing required files, duplicate IDs and dangling or out-of-package local references.
2. Provide a valid example, invalid fixtures, readable diagnostics and a machine-readable pass/fail result. Include an independent example read-through.

## Exclusions

Backup coverage and tamper verification ([8](./8.md)), app adapters, installer behavior, runtime execution and compatibility certification.

## Acceptance criteria and verification scenarios

1. With the network disabled, the example passes using schemas matched to `formatVersion`; an unsupported version fails clearly without fetching a replacement.
2. Check fixtures with malformed JSON, a missing field or file, a duplicate ID, a dangling reference and an out-of-package path separately. Each fails with the location and reason. Valid shared and unassigned references pass.
3. Give an independent reader the valid package and instructions alone. They can explain the agents’ behavior and follow the instructions, memories, skills, tools and routine references.

## Constraints and dependencies

Do not execute bundled code or resolve remote dependencies. Provide a `validate <package-dir>` command and `--json` flag. A valid package exits 0; invalid input exits 1; invocation or internal errors exit 2. JSON stdout contains `valid` and an `errors` array; each invalid-package error has a stable `code`, a package-relative `path`, a `message`, and a JSON Pointer when a field is attributable. Human output uses the same diagnostics. Resolve only the bundled schemas, and reject local symlinks or references outside the package. Depends on [1](./1.md) and the example in [3](./3.md). Implementation language is not part of the format.
