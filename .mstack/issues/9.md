## Problem and goal

Agent platforms (such as OpenBot, GrokBot, and CLI harnesses) store an agent's instructions, memories, skills, tools, and routines in incompatible, app-specific layouts. Users who want to capture their agents and move across platforms—or later publish agents without lock-in—are currently forced to rely on each platform's own export format.

Deliver the minimal, lightly opinionated Agent Files specification and its companion agent-facing `SKILL.md` so any agent can read the skill and autonomously capture itself (or a requested set of agents) into a clean, harness-agnostic directory structure (for example, in a GitHub repository), and another agent in a different harness can read those files and recreate the agent in its own native layout.

## In scope

1. **Lightly opinionated specification (`SPEC.md`):** Define the common-denominator directory layout and file conventions for the six concepts shared across agent harnesses:
   - Identity and metadata (such as `agent.json` for id, name, model, and resource references)
   - Standing instructions (such as `instructions.md`)
   - Memories (portable agent memories, kept separable so users can omit them before public sharing)
   - Skills (reusable `SKILL.md` folders referenced rather than duplicated per agent)
   - Tools and integrations (capabilities and external services the agent uses, without credentials or runtime wiring)
   - Routines (schedule or trigger such as cron with timezone, participants, and prompt)
   - Explicit gap reporting for items the source harness hides or makes inaccessible (such as abstracted skills or another agent's private memories).
2. **Agent-facing skill (`skills/agent-files/SKILL.md`):** Document the spec for an agent so the agent itself acts as the adapter in both directions (capturing from its current harness into Agent Files, and interpreting Agent Files into its target harness).
   - Guide autonomous capture with no required interactive Q&A loop, while honoring any extra instructions the user includes in their prompt (such as excluding memories, targeting multiple agents, or suggesting a GitHub repository for backup).
   - Enforce safety boundaries: never write credentials, tokens, or secrets; caution about personal memories in public repositories; log explicit gaps instead of fabricating or silently omitting invisible items.
   - Establish a `skills/agent-files/references/` structure for progressive per-harness lookup hints (starting with initial reference notes for known harnesses, such as OpenBot and standard local/global CLI skill paths) without coupling the spec or core skill to any single harness.
3. **Clear repository entry (`README.md`):** Summarize the convention, folder structure, and how to point an agent at the skill.

## Out of scope

1. Deterministic converters, CLI validators, JSON Schema enforcement suites, SHA-256 integrity-receipt tooling, or Node.js runtime dependencies.
2. Synthetic multi-domain example packages used as a substitute for a real-agent trial.
3. Harness-specific installers, runtime adapters, schedulers, team/org protocols, or marketplace hosting.
4. Prescriptive re-run, diff, or sync procedures (users decide how often and whether to re-run or update files).

## Constraints

1. The spec itself must remain harness-agnostic; harness-specific discovery details belong only in optional `skills/agent-files/references/<harness>.md` files.
2. Keep the format lightly opinionated rather than strict or deterministic so agents in different harnesses can map concepts naturally without forced schema compliance.
3. Never include credentials, tokens, chat transcripts, or runtime execution logs in captured definitions or QA artifacts.

## Acceptance criteria

1. **Spec coverage and simplicity:** `SPEC.md` clearly defines the directory layout and conventions for all six common concepts (identity, instructions, memories, skills, tools/integrations, routines) plus explicit gap reporting, without requiring any specific harness, validator, or converter.
2. **Autonomous agent-facing skill:** `skills/agent-files/SKILL.md` teaches an agent the spec, supports autonomous backup of one or more requested agents (including suggesting a GitHub repository when appropriate), prohibits secrets, cautions about memories in public repositories, requires explicit gap reporting, and links to optional progressive `references/` notes.
3. **Real-agent autonomous capture test:** A real agent running in an actual harness (starting with OpenBot; expandable to GrokBot or a CLI harness) is pointed at the skill and asked to back itself up (or a requested set of agents) into a target directory or private repository without interactive hand-holding. The resulting files faithfully represent how the agent behaves, remembers, and works in the Agent Files layout, leak zero secrets, and explicitly list anything the harness prevented it from inspecting.
4. **Independent cross-harness interpretability:** An independent QA actor (without this chat context) reads only `SPEC.md` and the real-agent backup output and accurately explains the agent's role, instructions, memories (if included), skills, tools/integrations, routines, and recorded gaps—and maps each piece to how they would recreate it in a different harness.

## Verification scenarios

1. **AC 1:** Inspect `SPEC.md` and `README.md`. Confirm all six concepts and explicit gap reporting are defined concisely and that no deterministic converter, validator, schema runtime, or required harness exists in the repository.
2. **AC 2:** Inspect `skills/agent-files/SKILL.md` and its `references/` files. Confirm an agent can follow the skill autonomously, secrets are forbidden, memory-privacy cautions and gap reporting are explicit, and harness-specific notes live strictly under `references/`.
3. **AC 3:** Point a real agent at `skills/agent-files/SKILL.md` with a single user prompt to back itself up to a disposable local path or private test repository. Compare the generated files against the agent's real instructions, memories, skills, tools, and routines; verify zero credentials/tokens appear and every inaccessible item is documented as an explicit gap.
4. **AC 4:** Provide only `SPEC.md` and the captured output from AC 3 to an independent QA actor. Verify they accurately summarize what the agent does, how it behaves, what was inaccessible, and how each file maps to an equivalent concept in another harness.
