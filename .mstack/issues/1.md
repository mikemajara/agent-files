## Problem and goal

Define a small, harness-independent folder format for moving standalone agents without losing their instructions, resources or memories.

## In scope

1. Document the package entry point, `config.json` with a required `formatVersion`, stable agent and resource IDs, and local reference rules. Use Markdown for instructions and routine prompts, and JSON for structured files, including agent-owned `memory.json` for supplied and learned memories.
2. Define shared skill packages, per-tool folders (configuration, bundled executable code, or external references), and routines with their own prompts. Resource assignment is explicit and does not enforce runtime access. MCP is optional.
3. Publish matching schemas in the spec repo, not in each agent package. Define required and optional fields and document how the version selects a schema set.

## Exclusions

Teams and groups, credentials, chat transcripts, run history, indexes, harness configuration and execution. Backup integrity is a companion concern in [8](./8.md).

## Acceptance criteria and verification scenarios

1. Given the spec and a sample package, an independent reader identifies all five primitives and follows their references without prior discussion or a harness.
2. Given matching schemas, a versioned sample passes field validation; removing a required field or substituting a wrong type fails at the affected field. The target package needs no schema directory.
3. Given two standalone definitions, they can share a skill or tool without duplication; a display-name change leaves references intact and supplied and learned memory entries use the same representation.

## Constraints and open decisions

Keep the format domain-neutral. Preserve `SKILL.md` conventions and source exports. Implement the following minimum contract; optional capabilities are absent rather than represented by null.

1. Root `config.json` requires `formatVersion` set to `"0.1"`; resource roots are `agents/`, `skills/`, `tools/`, and `routines/`. The spec repository publishes the JSON Schema set for `0.1`; an agent package does not bundle schemas. Use JSON Schema Draft 2020-12.
2. Agent `agent.json` requires `id` and `instructions`; optional `name`, `model`, `memory`, `skills`, `tools` and `routines`. `name` and `model` are strings. `instructions` is `instructions.md`; `memory`, when supplied, is `memory.json`. Memory files are arrays of nonempty strings, with no distinction between supplied and learned entries. Omitted resource lists mean no selections.
3. IDs use lowercase ASCII letters and digits in segments separated by single hyphens. An ID equals its directory name and is unique within its resource kind. References use the ID within that kind; display names do not participate in resolution. Resource lists contain distinct IDs. Local file references must stay inside the package and must not traverse symlinks.
4. A skill is `skills/<id>/SKILL.md` with optional supporting files. A tool is `tools/<id>/tool.json` with required `id` and `description`, optional non-secret `config` object and optional `source` string for an external reference; supporting code and setup notes can live in the tool folder. An integration is described as a tool; MCP is not required.
5. A routine is `routines/<id>/routine.json` with required `id`, `trigger`, `prompt`, `participants` and `result`, plus optional `skills`. `trigger` and `result` are nonempty descriptive strings; timed triggers name a timezone. `prompt` is `prompt.md` in the same folder. `participants` is a nonempty list of distinct agent IDs for that routine only. Definitions contain no activation state.
6. Match fields, types and fixed values with schemas; check cross-file IDs, paths, path containment and reference targets separately. Schema validation never needs network access or executes a bundled tool. Report unknown format versions rather than silently applying another schema set.
